# Proposed Unified Dataset Schema (Preliminary — Not Implemented)

This is a proposal only. No unified dataset has been created, and no raw file has been transformed, merged, or relabelled. The schema below is a planning artifact for a future phase, based solely on the structures found during the Phase 1 audit (`reports/dataset_audit.md`).

Each field below is marked:

- **ORIGINAL** — copied as-is from a source dataset's own field.
- **DERIVED** — would need to be computed, mapped, or annotated later; does not exist as-is in any source dataset.

| Field | Meaning | Origin | Why it matters |
|---|---|---|---|
| `record_id` | A unique identifier for this row in the unified dataset. | DERIVED | The audit found that source id fields are not reliably unique or comparable across datasets (e.g. AICompanionBench's `id` identifies a Reddit *post*, not a unique excerpt; CompanionHarm's `utterance_id` is only unique within CompanionHarm). A fresh, collision-free id is needed to reference any row unambiguously. |
| `source_dataset` | Which of the six audited sources this record came from (e.g. `companion_harm`, `chatbotmanip`). | DERIVED | Every downstream decision (what the label means, what unit it applies to, real vs. synthetic) depends on knowing the source; this must be tracked because the datasets are not equivalent. |
| `conversation_id` | The source dataset's own conversation/transcript identifier, where one exists (`uuid` in ChatbotManip, `conversation_id` in CompanionHarm, `IDs` in CLAIM, `id`/source-post in AICompanionBench, absent in TEA-Dialog's per-scenario structure — would map to `task_id`). | ORIGINAL (copied from source, field name varies) | Needed to reconstruct full conversations/transcripts and to preserve or check split integrity (the audit already confirmed no CompanionHarm split leakage using this field). |
| `turn_id` / `line_number` | Position of this record within its conversation, where the source has one (CompanionHarm has `line_number`; ChatbotManip turns are ordered list positions in `cleaned_conversation`; AICompanionBench and CLAIM have no per-turn structure since their unit is a whole excerpt/transcript). | ORIGINAL where available, DERIVED (e.g. list index) otherwise | Turn order matters for reconstructing context and for deciding whether a label is utterance-level, span-level, or whole-conversation. |
| `speaker` | Who produced this text: e.g. `Replika`/AI, `User`/human, `USER`/`AGENT`, or not applicable (CLAIM's `Primary Manipulator` is a role within a transcript, not a per-line speaker tag). | ORIGINAL where a speaker field/prefix exists; DERIVED (parsed from free text) for AICompanionBench, where speaker is only present as a `"User:"`/`"AI:"` text prefix. | The project's core question — is the *AI* being manipulative, or is it responding to manipulation — cannot be answered without knowing which party produced each line. |
| `text` | The actual utterance/turn/span/transcript text being labelled. | ORIGINAL (`current_line` in CompanionHarm, `content` in ChatbotManip's `cleaned_conversation`, `conversation` in AICompanionBench, `Dialogue` in CLAIM, message `content` in TEA-Dialog) | The unit being classified; field name and granularity vary by source, which is exactly why `annotation_level` (below) must be tracked alongside it. |
| `context` | Preceding conversation history available for this record, where the source provides it (CompanionHarm has an explicit `context` column; ChatbotManip's full history is in `cleaned_conversation`/`chat_completion`; AICompanionBench context is only whatever is inside the excerpt itself; CLAIM's "context" is the whole transcript up to that point). | ORIGINAL where a distinct context field exists; DERIVED (reconstructed) otherwise | Manipulation is often only interpretable with context (e.g. guilt-tripping following a refusal); losing context risks mislabelling benign lines. |
| `source_dataset` original label field name(s) | e.g. `Category_Final`, `label`, `Manipulative`, `manipulation_type`, `manipulative_*` | — (see below, not a schema field itself) | Recorded via the two fields immediately below rather than as one column, since sources use different field names and value sets. |
| `original_label` | The exact, unmodified label value as it appears in the source file (e.g. `h. Manipulation`, `Sexual misconduct`, `1`, `Gaslighting`). | ORIGINAL | Preserves the source's own judgment verbatim, per the audit's instruction not to invent or normalise labels; needed for traceability and for any later re-derivation. |
| `original_label_definition` | A short, written description of what the source dataset itself says this label means (e.g. from a paper, codebook, or column semantics inferred during the audit). | DERIVED (written once per unique label during schema population, not invented per-row) | The audit found labels with the same name (e.g. "Control") are not necessarily defined the same way across datasets; this field prevents silently treating them as equivalent. |
| `manipulation_label` | A project-level judgment of whether this record represents emotional manipulation, under a schema still to be defined (e.g. yes/no/unclear, or a taxonomy of manipulation types). | DERIVED | This is the project's actual target variable. It does not exist in any source dataset in a directly usable, consistent form — Section 10 of the audit shows original labels only map to it with varying confidence (`directly manipulation-related`, `potentially related`, `not manipulation`, `unknown`). |
| `manipulation_technique` | The specific tactic involved, if applicable (e.g. gaslighting, guilt-tripping, peer pressure, emotional blackmail). | ORIGINAL where the source already names a technique (ChatbotManip's `manipulation_type`, CLAIM's `Manipulation Techniques`); DERIVED otherwise (e.g. CompanionHarm and AICompanionBench have no technique sub-typing, only a coarse "Manipulation" category). | Needed if the project aims to detect not just "is this manipulative" but "what kind" — currently only two of five real datasets provide this. |
| `target_vulnerability` | What emotional state or need the manipulation (if any) appears to exploit (e.g. loneliness, fear, guilt, desire for companionship). | DERIVED | Not present in any source dataset; would require new annotation. Relevant to the project's goal of distinguishing manipulation from genuine emotional support, since both can target similar emotional states with different intent. |
| `annotation_level` | Whether the associated label applies to the whole conversation/transcript, a single utterance/turn, or a text span. | DERIVED (recorded per source dataset, not per row, based on Section 3 of the audit) | The audit found this varies by dataset (CompanionHarm: utterance-level; ChatbotManip: span-level; AICompanionBench and CLAIM: whole-excerpt/transcript-level; TEA-Dialog: no manipulation label at all). Mixing levels without tracking this would silently misrepresent what a label actually covers. |
| `annotator_count` | Number of human annotators who produced the label, where documented. | ORIGINAL where present (CompanionHarm's `annotator_count`; ChatbotManip has 8 distinct annotators across survey responses but no per-row count field, so this would need deriving); DERIVED otherwise | Signals label reliability; a label from 3 agreeing annotators (CompanionHarm) is not the same evidentiary strength as an unlabelled or single-source category value (AICompanionBench, CLAIM). |
| `agreement` | Level or type of annotator agreement, where documented (CompanionHarm's `agreement_type`, e.g. "2-way agreement"/"3-way agreement"). | ORIGINAL where present; DERIVED (not computable) otherwise | Same rationale as `annotator_count` — most sources provide no agreement information at all, which is itself an important limitation to carry forward rather than ignore. |
| `real_or_synthetic` | Whether the underlying conversation is a real human–AI (or human–human) interaction or an LLM-generated simulation. | DERIVED, but based on explicit documentation found during the audit (AICompanionBench and CompanionHarm are real Reddit/Replika logs; ChatbotManip and TEA-Dialog are explicitly LLM-generated; CLAIM's provenance as human–human courtroom transcript is documented but its manipulation labelling process is not) | The project goal concerns human–AI conversation; conflating real and synthetic data without tracking this would overstate how much real-world manipulation data actually exists. |
| `domain` | The setting of the interaction (e.g. AI companion app, decision-support assistant, emotional-support assistant, legal/courtroom human dialogue). | DERIVED (assigned per source dataset) | CLAIM in particular is not a human–AI dataset at all; this field prevents it from being silently treated as equivalent evidence to the AI-conversation datasets. |
| `split` | Which train/dev/test partition (if any) this record belongs to, and from which source. | ORIGINAL where the source already defines one (CompanionHarm's `split` column, confirmed leak-free by this audit); DERIVED otherwise (the other four usable datasets ship no split at all) | A future modelling phase will need to decide splitting strategy for datasets that currently have none, and must not silently reuse CompanionHarm's split boundaries for unrelated data. |
| `privacy_flag` | Whether this record contains fields identified as potentially identifying (e.g. AICompanionBench's Reddit `author`/`author_fullname`). | DERIVED | Section 12 of the audit found real, non-anonymised author metadata in AICompanionBench; this flag ensures such records are handled deliberately in any later cleaning/release step rather than passed through unnoticed. |

## Notes on scope

- This table is a **proposal**, produced from the audit findings only. It does not imply that all six sources will ultimately be merged, or merged in this exact shape.
- Several DERIVED fields (`manipulation_label`, `manipulation_technique` for datasets that lack one, `target_vulnerability`) represent genuinely new annotation work, not a mechanical transformation of existing labels — the audit is explicit that original labels must not be force-mapped into a manipulation category without justification (see Section 10 of `reports/dataset_audit.md`).
- Fields with no equivalent in a given source dataset (e.g. `annotator_count`/`agreement` for AICompanionBench and CLAIM) should be left explicitly null/unknown in that unified row, not backfilled with an assumed value.
